# 软件有效期与授权恢复设计（大方向）

> 目标：给交付出去的软件设一个有效期（如半年），到期自动失效，并提供一条**只有你能签发**
> 的恢复通道。
>
> 本篇只定大方向和信任模型，**不列字段格式 / 代码结构 / 接口细节**——那些等方向拍板后
> 另起实现文档。
>
> **评审结论（2026-08-03）**：按两期交付，**第一期只做可离线闭环，并首先接入
> `D:/git/zuche`**；第二期再做在线续期、措施广播和其它产品接入。第一期不依赖域名、G10 或
> toolkit-server，上线后即可单独验收。

---

## 0. 要解决的四件事

1. **在线验证**：能连到服务端时，怎么校验、怎么自动续期
2. **离线验证**：断网 / 内网 / 你的服务挂了时，怎么校验
3. **过期复核**：发现过期后，怎么恢复回可用状态
4. **域名与证书**：域名一年一续、证书 90 天一换，还可能被 MITM——这套东西怎么才不会被
   自己的基础设施拖死

其中第 4 条决定前三条能不能站得住，所以先讲它。

---

## 1. 信任模型（最重要的一条）

### 1.1 结论先行

**信任根 = 你的签名私钥，不是域名，不是 TLS 证书。**

授权的真伪由**应用层签名**决定：任何一份授权、任何一个服务端响应，都是你的私钥签过的，
客户端用编译进二进制的公钥验签。TLS 只负责传输保密，**不承载任何授权真实性**。

### 1.2 为什么不能靠 TLS

你们自己在 net-policy 里已经证明过了：把一张自签 CA 装进系统信任库，就能对任意 HTTPS
做中间人，明文解密并改包。所以如果授权逻辑是这样的——

```
客户端 → https://你的域名/verify → 返回 {"ok": true}   ❌
```

——客户只要 MITM 一下，让这个接口永远返回 `ok: true`，授权就废了。**成本：装个证书，
改个 hosts。** 这不是理论风险，是你自己手上就有的工具。

正确的形态是：

```
客户端 → 任意通道（HTTPS/HTTP/U盘/微信传文件都行）
        ← 一份你私钥签过的授权令牌
        客户端本地验签 → 签名不对就是假的                ✅
```

MITM 能看到、能改、能重放，但**造不出有效签名**。通道彻底不可信也无所谓。

### 1.3 三条不变量

| 不变量 | 含义 |
|---|---|
| **身份永不变** | 签名公钥编译进二进制，一次定终身。它不需要续期、不会过期、不依赖任何第三方 |
| **但私钥可被撤销** | "永不变"指的是**信任锚集合**，不是"某把私钥永远有效"。见下方泄露恢复 |
| **地址可以变** | 域名、IP、端口都是「地址」，随时可换，换了不影响信任 |
| **通道可以烂** | TLS 证书过期、被 MITM、甚至完全没有 TLS，都不影响授权的真伪判定 |

**推论：绝对不要做证书 pinning。** 你的证书 90 天一换，pin 上去就是给自己埋定时炸弹。
要 pin 就 pin 应用层签名公钥——信任锚集合稳定，而不是某张证书。

### 1.4 私钥泄露怎么恢复（"永不变"的例外）

"公钥编进二进制、一次定终身"是**可用性**的保证，但不能等于"私钥泄露也没救"——那是把
单点风险粉饰成不变量。正确模型是**多公钥 + 可撤销**：

客户端编进的是**一组带 key-id 和角色的公钥**（`kid → (pubkey, role)`），**光有私钥不够，还得
是"对的角色"才能干对应的事**——这是撤销模型能成立的关键：

| 角色 | 能签什么 | 保管 |
|---|---|---|
| `root` | **只签授权令牌 TKL1** | 离线主私钥 |
| `renewal` | 续期令牌（受限 TKL1）+ 在线响应封套 TKR1 | G10 在线（权限受限） |
| `directive` | 措施 TKD1 里的**地址/公告/kill/撤销某 lic_id/min_version** | 离线（发措施时用） |
| `recovery` | **唯一的高权恢复角色**：撤销其它 kid + 签 clock-reset（§5.1）+ 独立序列不受普通 seq 压制。**只干这几件恢复类操作** | 冷备，离线锁死、平时绝不用 |

客户端强制的角色规则：

- 验签时不仅查"kid 未撤销"，还查"**这个角色配不配签这种对象**"——`renewal` 签的 TKD1、
  `root` 签的撤销指令，一律拒绝。
- **撤销 kid 是 `recovery` 专属**。于是：泄露了 `root`/`renewal`/`directive` 中任何一把，
  攻击者都**撤不掉你的 `recovery`**（他没有那把私钥，且别的角色无权撤 kid）；你却能用
  `recovery` 撤掉他手里那把。
- 撤销集合**只增不减、单调并集**（见 §2.5），撤了就不可逆——防"漏写旧条目意外解封"。

泄露应对流程：`recovery` 签一条"撤销泄露 kid"指令下发 → 客户端此后拒收该 kid 一切令牌 →
用另一把 `root` 私钥重签在用令牌（首发就编 ≥2 把 root 公钥备用）。

> 准确表述：**信任锚集合不变，集合里每把钥匙可被撤销，但"撤销权"锁死在离线冷备的 recovery
> 角色上**。这才是"攻击者撤不掉你的冷备钥"能成立的前提——不是靠"他没有"，是靠"就算他有别的
> 钥匙也无权撤"。

## 2. 三条线怎么摆

### 2.1 地基是离线，在线是加速

```
   ┌─────────────────────────────────────────────┐
   │  离线线（地基）：签名令牌 + 本地验签         │  ← 永远可用，永不依赖你的服务
   │  ─────────────────────────────────────────  │
   │  在线线（加速）：连得上就自动续期/吊销/校时  │  ← 锦上添花，连不上不影响
   └─────────────────────────────────────────────┘
```

**顺序不能反。** 如果做成「必须联网才能用」，那么你的域名过期那天、G10 断网那天、
证书续期失败那天，所有客户同时停摆——这个故障半径你承担不起。

### 2.2 离线线（必须有）

一份自包含的签名令牌，里面写着产品、有效期、绑定的机器、功能范围。客户端启动时本地验签
+ 比对时间和机器，得出状态。全程不联网。

**防调系统时间**：本地记一个「见过的最大时间」水位，多处存放取最大值。发现当前时间明显
早于水位就判时钟异常，按已过期处理。这挡不住高手，但挡住 99% 的人，成本极低。

### 2.3 在线线（有则更好）

连得上服务端时做三件事，**每一件失败都静默忽略**：

| 动作 | 价值 |
|---|---|
| **拉新令牌** | 你后台改个到期日，客户下次启动自动恢复——**续期零沟通成本**，这是在线线唯一的核心价值 |
| **拉吊销名单** | 授权泄露 / 客户欠费时下发吊销（**尽力而为，非即时保证**，见下） |
| **校时** | 用**签名且绑定本次请求**的时间证明校正本地水位（见下） |

**密钥分层（回应「只有你能签发」）**：按角色分私钥（§1.4）——`root` 离线签授权、`directive`
离线签措施、`recovery` 冷备签恢复；只有 `renewal` 在 G10 在线，且**只能推进已有 lic 的
`expires_at`/`lease_until`（且不得越过令牌里 root 签死的商务截止），改不了机器/功能位**。所以
"零沟通续期"和"主私钥离线"不矛盾——G10 那把 renewal 泄露也造不出高权令牌、延不过商务截止。
详见实现文档 §6.2。

**吊销的及时性有天花板，用"三个日期"把它讲清**（回应 codex：区分授权上限/当前截止/在线租约）：

- `business_deadline` = **商务上限**（合同总期，比如一年）。**root 签死、不可变**，客户端锚定它。
  它是"这份授权最多能延到哪天"，续期永远越不过它。
- `expires_at` = **当前生效截止**（比如现在给到 3 个月后）。**续期时被 renewal 往后推**，封顶在
  `business_deadline`。**"后台改到期日自动恢复"改的就是它**——不是改商务上限。
- `lease_until` = **在线租约到期**（比如 7～30 天）。"多久必须在线续签一次"，可空。

> 所以"后台改到期日"有两种，别混：① 在商务上限内续命 → 调 `expires_at`（renewal 现签，零沟通）；
> ② 延长商务总期 → 必须 `root` 重签一份新锚（`business_deadline` 变了，走离线签发）。台账里
> `business_deadline` 与"当前该给到多久"（如 `grant_window_days`）分开存，续期 = 把 `expires_at`
> 推到 `min(now + grant_window, business_deadline)`。

`lease_until` 是可选的、按部署选的**"用离线换及时吊销"的旋钮**：

| 模式 | 令牌带 `lease_until`? | 离线能撑多久 | 吊销最坏窗口 |
|---|---|---|---|
| **纯离线**（默认，你本人/服务都不在也能用） | 否 | 直到 `expires_at`（半年） | 只能等自然到期或商务截止；**不保证及时吊销** |
| **可及时吊销**（要能远程关的客户） | 是 | 直到 `lease_until`（短），到期须在线续租 | **≈ `lease_until` + 宽限期** |

**这俩不能兼得**：要纯离线的韧性，就放弃及时吊销；要及时吊销，就得牺牲长时间纯离线。
选哪个是**按客户**定的（写进台账），不是全局。**文档不再笼统说"设较短 TTL"**——纯离线模式压根
没有短 TTL。承诺口径按模式分开说，别再混成一句：

- **可及时吊销（带 `lease_until`）**：吊销 = **服务端拒绝续租**，最坏窗口 = **`lease_until` + 宽限期**，
  租约到期客户端自然进受限，**不需要它主动拉到吊销指令**（服务端不发新租约即可）。
- **纯离线（不带 `lease_until`）**：令牌侧吊销**只能靠客户端成功拉到 `revoked` 指令**才生效，拉不到
  就一直用到 `expires_at`。
- **两种模式都能被服务端闸门（§2.4）即时关掉**——那是唯一"即时"的手段，前提是相关功能走服务端。

**在线响应必须签名且绑定请求**：服务端返回的令牌/时间都要带签名 + 一个**本次请求的 nonce**，
否则 MITM 重放一份旧的"未过期"响应就能续命，或伪造"时钟异常/已过期"制造拒绝服务。
**校时口径统一为**：水位**默认只单调增加**；**下调水位只在"满足误拨恢复判据的签名响应"下允许**
（在线 renewal 签的 TKR1、或离线 recovery 签的 clock-reset，见实现文档 §5.1）。所以正常在线校时
不会放宽授权，唯一的下调是"你自己签名授权的时钟纠错"——不是攻击面。

### 2.3.1 在线活动必须"随机"，不能固定时刻请求

**绝不能所有客户端都在同一个固定时间（如每天 0 点、整点）去请求。** 三个理由：

1. **惊群（thundering herd）**：客户装多了，固定时刻会把请求全怼到同一秒，把你的
   G10 / 域名入口打出一个尖峰，平时闲、点上炸。
2. **可预测 = 好封锁 / 好指纹**：固定周期的请求在网络侧是一个规整的心跳，容易被防火墙
   识别成"某软件在打点"，也容易被客户的网管盯上限流。
3. **抖动能摊平重试**：某个入口临时抽风时，错峰的客户端会自然分散重试，不会一起雪崩。

具体怎么"随机"（都很便宜）：

| 手段 | 做法 |
|---|---|
| **相位按机器散列错峰** | 用 `机器指纹 hash % 周期` 决定这台机器的基准触发点，让每台机器**稳定但彼此不同**——不是每次纯随机（纯随机会导致这台机今天早明天晚，不利于排查） |
| **叠加随机 jitter** | 在基准点上再 ±一个随机偏移（如 ±25%），彻底打散尖峰 |
| **间隔本身带范围** | 续期/校时的周期不是"恰好 24h"，而是"18~30h 里随机取一个"，下次再重取 |
| **首次延迟** | 启动后不立即打点，随机等 30s~几分钟再发首个请求，避免开机潮 |
| **失败退避也带抖动** | 重试用指数退避 + 随机抖动（full jitter），不要固定 1/2/4s |

一句话：**周期 = 一个区间内的随机值 + 按机器错峰的相位 + 每次叠加 jitter**，
对外表现为"这台机大约每天联一次，但没有任何两台在同一秒、也没有哪台卡在整点"。

> 注意边界：随机化只针对**在线线的时机**（续期/吊销/校时这些"锦上添花"的动作）。
> **本地验签、时钟水位判定是每次启动同步做的，不受随机化影响**——不能因为"这次没到
> 随机的联网点"就跳过本地授权检查。

### 2.4 想要真正硬的防护，只有一条路

客户端本地校验，**在有能力的逆向者面前一定能被 patch 掉**。这一点没必要自欺欺人。

真正绕不过的做法是：**让软件离了你的服务端就没有核心价值**。你的架构天然接近如此——桌面端的
ASR / TTS / LLM 能力实际都在 G10 的 toolkit-server 上（**RAG 是独立 `rag` binary，当前未挂进
toolkit-server 路由，要纳入闸门需另接**）。

但要落地这层闸门，**现状还差一步**：`toolkit-server` 现在的鉴权是**单一共享 `TOOLKIT_API_TOKEN`**
（[auth.rs](../crates/toolkit-server/src/auth.rs)，**未配置时完全放行**，且 internal/exec 等路径另有豁免）。
它认不出"哪个客户"。所以硬闸门要先补一件事：**引入 per-客户 / per-设备 token，并建立
token → `lic_id` 映射**，才能在鉴权之后判"这个 token 对应的授权还有效吗"。补齐后改二进制也没用，
因为算力和数据在你手里。代价是这部分功能必须联网 + 一套客户身份体系（见实现文档 §6.2）。

**推荐分工**：
- 纯本地功能 → 离线令牌管（体验好，但可被逆向绕过，认了）
- 值钱的服务端能力 → 服务端闸门管（硬）

### 2.5 措施下发通道（签名指令文件，多镜像 pull）

前面 §3.3 的"入口清单"其实只是**一类**措施。把它泛化成**一个你签名过的指令文件**，
挂在多镜像静态托管（**Gitee raw / git / OSS 对象存储**）上，客户端按随机时机 pull、
验签、执行。**你的服务器不在线也能下发**——这是它和「在线线」（§2.3，走 toolkit-server）
最大的区别：在线线要服务在，这条通道只要一个能放文件的地方在。

一个 `directives.json`（签名后 = `TKD1.<payload>.<sig>`）能带的"措施"：

| 措施 | 用途 |
|---|---|
| **入口清单** | 换域名/IP，老客户端自动改道（§3.3） |
| **吊销名单** | 某 `lic_id` 泄露/欠费 → **对成功拉到本指令的客户端加速吊销**（非即时全网，§2.3） |
| **撤销 kid** | 某签名公钥泄露 → 拒收该 kid 一切令牌（**仅 recovery 角色可签**，§1.4） |
| **最低版本 / 强制升级** | 低于某版本弹更新、甚至进受限 |
| **公告 / 通知** | 给客户端弹一条你签名的消息（维护通知、续费提醒） |
| **紧急开关** | 极端情况全局降级（谨慎，见下） |
| **服务端地址轮换 / 校时基准** | 配合在线线 |

四条硬约束：

0. **角色分权**：撤 kid 只认 `recovery` 签的指令，其余措施认 `directive` 角色（§1.4）；
   验签同时校验"角色配不配签这种措施"。
1. **只认签名**：验签不过整份丢弃，绝不"部分执行"。托管处被污染/被接管也塞不进假措施。
2. **两套独立序列，恢复通道不被普通指令压制**：`directive` 措施走 `seq`（客户端存 `last_seq`，
   只收 `seq > last_seq`）；`recovery` 的撤 kid / clock-reset 走**另一条独立 `rseq`**（存 `last_rseq`）。
   否则拿到泄露 `directive` 私钥的攻击者只要签一条 `seq = u64::MAX` 的普通指令，就能让此后所有
   合法撤钥指令都卡在 `seq >` 判断上——**恢复通道被永久堵死**。分开序列后，普通指令刷再高也压不住
   recovery。撤销集合（`revoked`/`revoked_kids`）仍**按并集累加、永久不可逆、没有 unrevoke**；撤错就
   换新 kid/lic 重发。但序列号只挡**网络侧**回放；**挡不住本机 root 回滚本地 `last_seq`/`last_rseq`**——
   本地状态对本机 root 不可信。所以吊销的强保证仍靠 `lease_until`（§2.3）+ 服务端闸门（§2.4），
   指令通道是"广播加速"，不是"不可回滚的强制"。
3. **紧急开关要有下限**：全局 kill 这种措施**永远不能锁死激活页和数据导出**（§4.1 红线），
   否则一次误操作 = 全网客户找你算账。

> 一句话：在线线（服务端）负责**一对一**（这台机的新令牌）；措施通道（静态文件）负责
> **一对多**（全网广播），且不依赖你的服务活着。两条通道内容都必须你签名。

## 3. 域名与证书怎么完善

这是你现在最脆的一环。

### 3.1 现状与风险

| 现状 | 风险 |
|---|---|
| 外网入口 `spark.for-memory.site:38788` 是**默认值**（`wan_host` 已是持久化、用户可在设置页改的字段，[settings.rs](../crates/zero-desktop/src/shared/settings.rs)） | 换域名不会立刻全体失联，但**无法自动迁移**——要么逐客户端人工改配置，要么发新版本，都很重。措施通道（§2.5）就是为了让老客户端**自动**改道 |
| caddy + acme.sh 续 `*.for-memory.site`（90 天一轮） | 续期一次失败 → 外网入口整体不可用 |
| 域名一年一续费 | 忘续 / 被抢注 / 被墙 → 同上，且可能被别人接管去冒充你 |
| 信任建立在 TLS 上 | 可被 MITM 伪造（§1.2） |

### 3.2 三层解耦

把「身份 / 地址 / 通道」彻底拆开，各自独立演进：

```
  身份层   签名公钥（编译进二进制）        永不变、无有效期、不依赖任何人
    ↑
  地址层   域名 / 备用域名 / 直连 IP       可换，换了要能通知到老客户端
    ↑
  通道层   TLS 证书（caddy/acme）          可过期、可被中间人，不影响信任
```

### 3.3 地址层怎么做到「可换」

核心是**别只有一个入口**。客户端内置一份**候选入口清单**，逐个尝试，任一通即可：

1. 主域名（现在的 `spark.for-memory.site`）
2. 备用域名（**不同注册商、不同后缀**，避免一起挂）
3. 直连 IP + 端口 —— **仅限"拉签名指令"这类不带凭据/敏感数据的请求**。⚠️ 通配证书通常
   不含 IP SAN，`https://<IP>` 会证书校验失败；要用它跑**业务**（带 Bearer/上传），必须
   要么给证书签 IP SAN、要么用一个保留域名 + 客户端本地覆盖它的 DNS 解析到该 IP。
   **不能把裸 IP 直接当业务入口**（否则要么校验失败、要么被迫降级明文泄露凭据，违反 §3.4）。
4. **一个静态托管的"最新入口清单"**——放在你不用维护的静态托管处，内容是一份
   **你签名过的地址列表**

第 4 条是关键：换域名时你只要更新那个静态文件，老客户端下次启动就能自动找到新地址。
因为清单是签名的，即便托管处被 MITM 或者那个仓库被人接管，也**塞不进假地址**。

> 这条链路只解决「找得到你」，不解决「授权真假」——授权真假永远由 §1 的签名决定。
> 所以清单托管在哪、走不走 TLS，都不敏感。

### 3.3.1 清单托管：Gitee 可以，但要"多镜像"而不是"换一家"

**面向大陆客户，GitHub Raw 经常访问不了，这是真问题**（`raw.githubusercontent.com` 在
大陆被污染/限速很常见）。Gitee 能替代，但它有自己的坑，**单独依赖它反而更脆**：

| Gitee 的坑 | 影响 |
|---|---|
| Raw 链接（`gitee.com/<user>/<repo>/raw/...`）要求仓库**公开**，且会校验 Referer/UA、有防盗链 | 客户端直连拉 raw 可能被挡，得留意 UA |
| **内容审查**：Gitee 会人工/自动审仓库，命中即**私有化或下架**，你收不到预警 | 入口清单突然 404 |
| 单点仍是单点 | 换汤不换药 |

**正确姿势是把「入口清单」同时放到多个互不相关的静态托管，客户端并列尝试**：

- **Gitee Raw / Gitee Pages**（大陆首选，主力）
- **国内对象存储**（阿里云 OSS / 腾讯云 COS 的一个公开只读 bucket，最稳，几毛钱一个月）
- **GitHub Raw / jsDelivr CDN**（`cdn.jsdelivr.net/gh/...`，海外客户或 Gitee 挂了时兜底）
- 甚至可以再塞一个自己的小 VPS 上的静态文件

因为**清单本身是你签名的**，放几家、哪家先响应、走不走 TLS，全都无所谓——最坏情况是
某几家被污染返回垃圾，客户端验签不过直接跳下一家。**托管处越杂、越互不相关，可用性越高**，
且没有任何一家能塞进假地址。这正是「通道可以烂」（§1.3）在这里的兑现。

> 一句话：Gitee 不是「替代 GitHub」，是「和 GitHub、对象存储一起，凑成一组冗余镜像」。
> 面向大陆就把 Gitee / 对象存储排在候选清单前面，GitHub 放最后当兜底。

### 3.4 证书层：对「授权真伪」无所谓，对「传输机密性」仍必需

**要分清两件事，别混为一谈**：

- **授权真伪** —— 由应用层签名保证，和 TLS 无关。证书过期/被 MITM，也伪造不出有效令牌。
- **传输机密性** —— 只能靠 TLS。请求里带的 **Bearer token**（[auth.rs](../crates/toolkit-server/src/auth.rs)，
  WS 甚至把 token 放 URL `?token=`）、业务数据、上传内容，**一旦降级明文就被 MITM 直接窃取/篡改/冒用**。

所以：

- 证书过期 → **不允许静默降级明文继续跑业务**。可以：暂停对外业务、显式告警、走备用入口重试；
  只有在**确无敏感数据**的探测类请求上才容忍明文。**默认 fail-safe，不 fail-open。**
- **不做证书 pinning**（§1.3，pin 上去 90 天一换就是定时炸弹），但这不等于「TLS 可有可无」——
  pin 的是**信任锚（用系统信任库 / 你自己的 CA）**，不是某张具体证书。
- acme 续期失败**降级为 P1**（不再是"全网停摆"的 P0，因为授权不依赖它），但仍要尽快修——
  它关系到凭据和业务数据的机密性。

这一步把「授权可用性」和「基础设施故障」解耦，但**机密性依旧依赖 TLS 健康**，不能一起丢掉。

### 3.5 域名本身的建议

| 事项 | 建议 |
|---|---|
| 续费 | 一次性续 **5～10 年**，年费几十块，换掉每年一次的忘续风险 |
| 备用域名 | 至少 1 个，**不同注册商、不同 TLD** |
| DNS | 用支持 API 的服务商，切换入口能自动化 |
| 所有权 | 注册信息、DNS 账号、acme 账号的凭据做离线备份——这是整条链的单点 |

## 4. 到期与恢复的大原则

### 4.1 到期不是"停用"，是分段降级

```
   到期日                +宽限期
 ────┼──────────────────────┼──────────────►
 临期提醒 │  宽限期（全功能+强提示） │  受限模式
```

- **宽限期（建议 14 天）**：功能不减，只是提示变强。现实里「续费流程走两周」是常态，
  硬到期会直接把客户推向找破解版。
- **受限模式**：关掉生产性功能，**保留只读和数据导出**。

**红线**：不删数据、不加密数据、不破坏环境。受限模式下**永远能进激活页**——
「打不开软件所以没法激活」是最糟糕的死锁。

### 4.2 恢复三级降级

| 方式 | 场景 | 你的介入 |
|---|---|---|
| **在线自动续期** | 常规 | 后台改个到期日，客户下次启动自动恢复。**零沟通** |
| **离线激活码** | 断网 / 内网 / 你的服务挂了 | 客户报一串机器码给你，你本地签一份发回（微信传都行） |
| **应急临时码** | 客户急用、你人在外面 | 按客户发来的机器请求串签一个短期、限功能码，先顶上 |

三条是目标态，但不要求同一期交付。**第一期先交付离线激活**；在线自动续期和应急流程在
第二期补齐。离线这条永远不能砍——它是「你的域名、服务器、甚至你本人都不在」时，客户唯一的
活路。所谓应急码也必须绑定机器；不提供“不绑机的万能短期码”，避免它变成可转发的后门。

### 4.3 邮件通知（带外提醒，别只靠自己记）

到期这件事最容易栽在「忘了」上。加一条**邮件通知**，由 toolkit-server 的 license 台账驱动
（它知道每一份 `expires_at`），定时扫描 + 触发事件时发信：

| 触发 | 收件人 | 作用 |
|---|---|---|
| **临期 T-30 / T-14 / T-7 / T-3 / T-1** | **你**（+可选客户联系人） | 主动续期，别等客户来催 |
| **已到期 / 进入宽限** | 你 + 客户联系人 | 走续费流程 |
| **吊销已下发** | 你 | 操作留痕确认 |
| **反复激活失败 / 时钟异常上报** | 你 | 早发现盗用或客户机器问题 |

要点：

- **发信方**：toolkit-server 内置一个轻量 SMTP 发送（`lettre` crate），配置走环境变量
  （`SMTP_*` + 收件人）。**未配置就不发**，和 TTS/LLM 一样是可选能力。
- **是带外提醒，不是控制通道**：邮件只用来"通知人去操作"，**绝不承载授权真假**
  （授权真假永远是签名，§1）。邮件可被伪造/丢失，不能让它决定客户端行为。
- **降噪**：同一 `lic_id` 的同类提醒做去重（每个阈值只发一次），别把自己淹了。
- **客户联系人**：存在 license 台账记录里（`contact_email` 字段），签发时录入。

## 5. 需要你拍板的几件事

| 问题 | 我的建议 | 理由 |
|---|---|---|
| **交付对象是谁** | **交付客户（已定）** | 走最强一档：绑机器 + 服务端闸门 + 分段降级都要，可被逆向绕过的部分认了 |
| **首次接入产品** | **zuche（已定）** | Linux web 服务形态先验证共享核心、机器绑定、受限路由和离线恢复闭环 |
| 是否绑机器 | 交付客户绑（允许 2~3 台），内部不绑 | 防一份授权全网传播 |
| 到期是全停还是保留只读 | **保留只读 + 可导出** | 纠纷成本低得多 |
| 是否强制联网 | **否** | 故障半径太大（§2.1） |
| 防护做到哪一档 | 远端能力用**服务端闸门**；客户本机能力止于签名授权 | zuche 本地部署可被 root patch；加壳 / 反调试性价比低且易误报 |
| 是否加编译期硬死线 | **不加** | 老版本被硬砖化会伤到你自己的存量部署 |
| 域名续费年限 | **一次续 5~10 年** + 至少 1 个备用域名 | 几十块钱买掉一个单点故障 |

## 6. 两期交付

### 第一期：离线授权闭环，先接 zuche

1. 在 `custom-utils` 增加无 UI、无网络依赖的授权核心：签名验签、机器请求串、时钟水位、状态机。
2. 提供离线签发工具；生产二进制只内置公钥，私钥不进入源码、CI、G10 或客户机器。
3. 在 `zuche-rs` 增加 `license machine/import/status`，并提供始终可访问的 web 授权页。
4. 在 axum 路由和后台生产任务上做能力级拦截：授权正常时不改变行为；宽限期全功能强提示；
   受限后禁止登录、验证、代发、同步和其它写操作，保留授权页、只读查看和数据导出。
5. 验收必须覆盖：无授权、坏签名、错机器、未生效、临期、宽限、过期、时钟回拨、导入新授权恢复；
   以及受限时生产接口被拒而授权/只读/导出仍可用。

一期明确不做在线续期、远程吊销、措施镜像、邮件和 zero-desktop 接入，避免把基础闭环与运营平台
绑在一起。zuche 当前没有完整的“已采数据导出”能力，因此一期必须新增对实际持久化 SQLite 数据的
只读导出入口；内存 `RunHistory` 不能冒充持久化数据。采集循环若不属于当前产品能力则不为授权功能
凭空新增，但任何已有或后续新增的后台生产循环都必须在每次动作前检查授权状态。

### 第二期：在线运营与扩展接入

1. 增加受限 `renewal` 角色、签名且绑定 nonce 的在线续期响应，并始终保留首次 root 授权作为不可变锚。
2. 增加多镜像签名措施、密钥撤销、入口轮换和邮件提醒。
3. 接入 zero-desktop；如果价值能力仍运行在我方服务器，再增加 per-customer/per-device 身份与服务端闸门。
4. 第二期不得改变一期的离线恢复能力；在线服务不可用时，已签授权仍按本地截止日运行。

服务端闸门只对“能力实际运行在我方服务器”的功能构成硬保护。zuche 整体部署在客户 Linux 服务器上，
其本地校验仍可被有 root 权限且愿意逆向的客户 patch，这一限制必须作为安全边界接受。

**可落地的实现设计（crate 结构、密钥体系、令牌/指令格式、接口、分阶段任务）见
[docs/license-impl-design.md](license-impl-design.md)。**
